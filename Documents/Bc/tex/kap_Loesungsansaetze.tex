\subsection{Analyse vorhandener Systeme}
Es existieren bereits einige Systeme, welche die gewünschten Funktionalität, teilweise oder ganz umsetzen. Folgend sollen diese betrachtet werden. Es soll geklärt werden, welche Funktionen übernommen beziehungsweise sinnvoll erweitert werden können.
\subsubsection{Native Instruments Reaktor}
\emph{Reaktor\footnote{http://www.native-instruments.com/\#/en/products/producer/reaktor-55/}} ist eine leistungsstarkes System, zum Erschaffen von Effekten und Synthesizern. Es gibt eine Vielzahl an Modulen, die frei ''verdrahtet'' werden können. Ab Version 5 ist es sogar möglich, eigene Module mittels DSP-Schaltungen zu entwerfen. Die Module werden durch Parameter gesteuert, welche in Form von Drehreglern, auf einem frei gestaltbaren Bedien-Panel platziert werden können. Die Bedienung ist zwar direkt und intuitiv, der Programm-Anfänger jedoch, ist schnell überfordert durch die Vielzahl an Funktionen und Modulen. Hier ist eine lange Einarbeitungszeit notwendig. Reaktor ist u.a. als VST-Plugin verfügbar, bietet aber keine Möglichkeit VST-Plugins zu Laden und zu Verwenden.
\subsubsection{Ableton Live}
\emph{Ableton Live\footnote{http://www.ableton.com/}} ist in erster Linie ein Sequenzer. Der Fokus liegt daher, auf dass erstellen von Musikstücken. Ähnlich zu Cubase, existiert hier ebenfalls das Spur/Mischpult-Prinzip. Effekte lassen sich somit ausschließlich nach vorgegebenen ''Bahnen'' verknüpfen. Einen interessanten Ansatz, bieten die sogenannten ''Makro-Regler\footnote{Ableton Benutzerhandbuch Version 8, Seite 270 f.}''. Diese erlauben es beliebig viele Bedienelemente, d.h auch VST-Pluginparameter, über einen ''Marco''-Regler zu steuern. Das Regelverhalten ist umkehrbar.
Die Benutzung solcher ''Makro-Regler'' ist wenig intuitiv. Um eine ''Makro''-Verbindung zu erstellen, sind mehrere Kontextmenü-Aufrufe an unterschiedlichen und teilweise unerwarteten Stellen notwendig. So muss zum Beispiel, um die ''Makro''-Funktion für ein Plugin zur Verfügung zu stellen, in dessen ''Rack''-Fensterrahmen die Kontextmenüfunktion ''Group'' aufgerufen werden. Dargestellt werden schließlich diese Verbindungen in einer Tabellen-Ansicht. Somit ist auf einen Blick nicht sofort erkennbar, welche Verbindungen bestehen. Dennoch ist der Zweck dieser Funktionalität interessant, nämlich verschiedene Parameter sinnvoll zu Gruppieren.  
\subsubsection{Metaplugin}
Das VST-Plugin \emph{Metaplugin\footnote{http://www.ddmf.eu/product.php?id=3}} erlaubt es, beliebig viele VST-Plugins, auf einer ''Bühne'' zu platzieren und beliebig miteinander zu ''verdrahten''. Darüber hinaus bietet es keine weiteren Funktionen. Dadurch ist es allerdings auch sehr gut bedienbar. Die gesamte Funktionalität kann in wenigen Minuten, allein durch Ausprobieren intuitiv erfasst werden.
\subsubsection{Zielsetzung}
Ziel ist ein System, welches einen Mittelweg zwischen dem \emph{Metaplugin} und \emph{Reaktor} findet. Es sollte ähnlich, dem \emph{Metaplugin} intuitiv bedienbar sein, aber dennoch über dass bloße Verknüpfen von Plugins hinaus, sinnvolle Erweiterungen, wie eine intuitive Parametergruppierung bieten. Eine \emph{Reaktor} ähnliche Modularchitektur sollte es ermöglichen, mit relativ wenig Aufwand, Erweiterungen - die das Plugin/Parameter Vernetzungskonzept erweitern - zu implementieren.

\subsection{Die Effektverkettung}
\paragraph{Das Modell}
VSTForx soll Plugins laden und mittels ''virtueller'' Kabel verbinden können. Als mathematisches Modell ist für diese Aufgabe der gerichtete Graph geeignet. Die Knoten repräsentieren die Plugins und die Kanten ihre Verbindungen. Eine gerichtete Kante entspricht einer Verbindung von Pluginausgang zu Plugineingang. 
\paragraph{\label{process}Die Berechnungsreihenfolge}
Wie bereits in Kapitel \ref{Prozess} beschrieben, erzeugt ein Plugin seine Ausgabe anhand einer ''processReplace'' Methode. Das Programm muss nun den beschriebenen Prozessablauf mit den geladenen Plugins durchführen. Doch in welcher Reihenfolge sollten diese Aufrufe stattfinden?\\\\
\begin{figure}[h]
	\centering
 	\includegraphics[scale=0.1]{../graphics/g01.png}
	\caption{Beispiel eines Plugin-Graphen}
	\label{g01}
\end{figure}
Gegeben sei folgendes Beispiel:
\\\\
Der erforderliche Prozessablauf für Abbildung \ref{g01} wäre:
\begin{enumerate}
	\item bereite Inputsampleblöcke für Plugin-A vor
	\item führe ''processReplace'' mit Plugin-A aus
	\item bereite Inputsampleblöcke für Plugin-B vor (mit der Ausgabe von Plugin-A)
	\item führe ''processReplace'' mit Plugin-B aus
	\item\label{PlugC}bereite Inputsampleblöcke für Plugin-C vor (mit der Ausgabe von Plugin-A und B)
	\item führe ''processReplace'' mit Plugin-C aus
	\item übertrage die Ausgabe von Plugin-C in die Programm(VSTForx) Ausgabesampleblöcke
\end{enumerate}
Wie in Schritt \ref{PlugC} zu sehen, ist zur korrekten Ausführung von Plugin-C notwendig, dass die Plugins A und C bereits bearbeitet wurden. Das bedeutet: Plugin-C ist von Plugin-A und Plugin-B abhängig. \\\\
In der Graphentheorie gibt es einen Algorithmus der in der Lage ist Abhängigkeiten aufzulösen: Die Topologische Sortierung.
\\\\
Die Topologische Sortierung basiert auf der Durchlaufstrategie Tiefensuche\footnote{oder auch DFS - engl.: Depth First Search}. \\
''Sie erzeugt eine lineare Anordnung von Knoten eines Graphen. Existiert eine Kante zwischen den Knoten (u, v),  so wird u vor v geordnet."\footnote{\label{bglTopo}vergl. \cite{bgl01}, S. 176 f.}\\
Das Resultat der Topologischen Sortierung ist daher, eine sortierte Menge an Knoten, deren Reihenfolge genau ihren Abhängigkeiten entspricht.
In unsrem Beispiel würde die Topologische Sortierung die gewünschte (Plugin-)Knotenmenge \{A, B, C\}\footnote{vorausgesetzt Knoten A ist der Startknoten der Topologischen Sortierung} ergeben. \\
Die Topologische Sortierung hat ein Laufzeitverhalten von $\mathcal O(|V| + |E|)$\footnotemark[13] \footnote{wobei |V| die Menge aller Knoten und |E| die Menge aller Kanten ist}, und ist somit eher ungeeignet um in Echtzeit sehr häufig ausgeführt zu werden. Allerdings ändert sich die Ergebnismenge auch nur dann, wenn sich der Graph verändert.
Die Ergebnismenge sollte daher ausschließlich nach einer Graphänderung erstellt und in einer Liste gespeichert werden. Solch eine ''Prozess-Liste'' wird während des Prozesses einfach iteriert. Somit ergibt sich eine Laufzeit von $\mathcal O(|V|)$.
\paragraph{Rückkopplungen}
Eine Einschränkung der Topologischen Sortierung ist es, dass die zu sortierenden Graphen keine Zykel enthalten dürfen. Dies hat für VSTForx zur Auswirkung, dass keine Rückkopplungen ''geschaltet'' werden können. Eine Rückkopplung wäre es zum Beispiel, wenn der Ausgang eines Plugins, direkt oder über Umwege, wieder an seinem Eingang liegen würde. Sollten Rückkopplungsschaltungen unterstützt werden, könnte man die betreffenden Knoten lokalisieren und durch einen Subgraphen substituieren. Dieser Subgraph könnte dann die Knoten durch einen alternativen Algorithmus, einen der Rückkopplungen unterstützt, bearbeiten. Dies ist jedoch, aufgrund der Komplexität des Problemes, nicht vorgesehen. 
\\\\
Die Topologischen Sortierung ist allerdings in der Lage zu erkennen ob ein Graph Zyklisch ist \footnotemark[13]. Zur Vermeidung von Fehlverhalten werden daher Zyklische Graphen nicht zugelassen.  \\

\subsection{\label{Latenzproblem}Das Latenzproblem}
\begin{figure}[ht]
	\centering
 	\includegraphics[scale=0.15]{../graphics/latenz.png}
	\caption{Darstellung des Latenzproblemes: die Signalausgabe aus ''Effekt B'' ist um 10 ms verzögert}
	\label{latenz}
\end{figure}
Werden Plugins parallel verbunden, kann es unter umständen zu einem Problem kommen:
es gibt Plugins die eine Latenzzeit größer 0 aufweisen. Das bedeutet die Pluginausgabe ist zeitlich verzögert.
Bei einer Parallelschaltung kann diese Latenz nun bewirken, dass zum Beispiel in einem Signalpfad eine Verzögerung auftritt, im anderen aber nicht (siehe Abbildung \ref{latenz}). Die Signale erklingen daher versetzt. 
\\\\
Um unterschiedliche Latenzen in einem komplexen Graph auszugleichen, wäre folgendes notwendig:
\begin{itemize}
	\item hinzufügen eines berechneten Latenzwert je Knoten
	\begin{description}
		\item[=] Maximaler Latenzwert der Vorgängerknoten, addiert zum eigenen (realen) Latenzewert
	\end{description}
	\item hinzufügen eines Buffers je Knoten, dessen Größe = Sampleblockgröße + berechneter Latenzwert ist.
	\item die Ausgaben aller Vorgängerknoten, je nach Vorgängerlatenz an unterschiedlichen Position, dem Buffer hinzufügen (siehe Abbildung \ref{dc})
	\item Sampledatenmenge des Buffer als Eingabe weiterverarbeiten
\end{itemize}

\subsection{Nebenläufigkeit}
Ein VST-Plugin kann optional einen Editor implementieren. Ein Editor ist ein eigenständiges Fenster, welches die Benutzeroberfläche des Plugins enthält und wird von der DAW bei bedarf geöffnet. Da Eingaben auf der Benutzeroberfläche zu einem unbestimmten Zeitpunkt geschehen, der Pluginprozess aber kontinuierlich (nebenläufig\footnote{ob als eigenständiger Prozess oder Thread ist DAW abhängig}) abgearbeitet wird, liegt hier ein Nebenläufigkeitsproblem vor. Wird der Effekt-Graph geändert, während er vom Prozess bearbeitet wird, kann dies ein undefiniertes Verhalten verursachen. \\
Folgend sollen drei verschiedene Lösungsansätze beschrieben werden:
\paragraph{Blockieren des Prozesses}
Es wäre möglich jede Graphverändernde Methode solange zu blockieren, wie die Prozessmethode abgearbeitet wird. Umgekehrt wird die Abarbeitung der Prozessmethode blockiert, solange eine Graphverändernde Methode abgearbeitet wird. Ein Verfahren welches solch eine Blockierung unterstützt ist das Mutex (siehe \cite{tan09}).
\\\\
\begin{lstlisting}[caption={Beispiel einer gegenseitigen Blockierung}]
	
class Graph {
private:
	Mutex mutex;
public:
	void veraenderGraph() {
		mutex.lock();
		// ...
		mutex.unlock();
	}
	
	void prozess() {
		mutex.lock();
		// ...
		mutex.unlock();
	} 
};	
		
\end{lstlisting}
Der Nachteil dieser Methode ist, je komplexer die Graphklasse und ihre enthaltenden Methoden, so höher ist die Gefahr dass es vergessen wird ein gesperrtes Mutex wieder zu entsperren (siehe Listing \ref{block02}). Ein Deadlock wäre die folge.
\\\\
\begin{lstlisting}[label=block02, caption=Beispiel eines potentiellen Deadlocks]
	
class Graph {
private:
	Mutex mutex;
public:
	void veraenderGraph() {
		mutex.lock();
		if (dings == bums) {
			return;	// !!
		}
		mutex.unlock();
	}
	
	void prozess() {
		mutex.lock();
		// ...
		mutex.unlock();
	} 
};	
		
\end{lstlisting} 
\paragraph{Das Befehl Entwurfsmuster}
Das Befehl Entwurfsmuster gehört zu den Verhaltensmustern der ''GoF'' Entwurfsmuster.  Es dient dazu Programmbefehle in einem Objekt zu Kapseln (vgl. \cite{gof04}). \\
Der Graph würde seine verändernden Befehle nicht mehr als öffentliche Methoden anbieten, sondern nur noch Befehlsobjekte entgegennehmen.
Solch ein Objekt würde dann vom Graph, zu einem sicheren Zeitpunkt (zum Beispiel nach Abschluss der Prozessmethode) ausgeführt (siehe Listing \ref{command}).

\begin{lstlisting}[label=command, caption=Lösung des Nebenläufigkeitsproblemes durch das Befehl Entwurfsmuster]

// Datei AenderGraph.h

#include "ICommand.h"
#include "Graph.h"

class AenderGraph : public ICommand {
friend class Graph;
private:
	Graph *graph;
public:
	AenderGraph( Graph *graph ) : graph(graph) {
	}
	
	virtual void execute() {
		graph->veraenderGraph();
	}
};

// Datei Graph.h
#include "ICommand.h"

class Graph {
private:
	void veraenderGraph() {
		// ...
	}
	typedef stack<ICommand*> Commands;
	Commands commands;
public:
	void addCommand( ICommand *cmd ) {
		commands.push(cmd);
	}
	void prozess() {
		// bearbeite Graph
		// ...
		while ( !commands.empty() ) {
			ICommand *cmd = commands.top();
			cmd->execute();
			commands.pop();
		}
	}	 
};	
\end{lstlisting} 
Da es möglich ist ein VST-Plugin über die DAW in einen Standbymodus\footnote{die Prozess Methode wird nicht mehr ausgeführt} zu schalten, kann es mit diesem Verfahren passieren, dass die entgegengenommenen Befehlsobjekte nicht mehr ausgeführt werden. Der Graph würde nicht mehr bearbeitet. Daher ist diese Vorgehensweise nicht geeignet.

\paragraph{Automatisches Blockieren und Freigeben}
Mittels Konstruktor/Destruktor Mechanismen ist es möglich eine Lösung zu entwerfen, die dafür sorgt, dass der Prozess automatisch blockiert und wieder freigegeben wird solange der Graph verändert wird. Realisiert wird dies durch eine Klasse die ''Janitor\footnote{engl.: Hausmeister}'' gennant wurde.
Die Janitor-Klasse enthält alle Graph verändernden Methoden. Der Konstruktor des Janitors blockiert die Prozessmethode, der Destruktor gibt sie wieder frei. Somit kann sichergestellt werden, dass solange ein Janitior-Objekt existiert der Graph nicht weiter abgearbeitet werden kann (siehe Listing \ref{janitor}).
\\\\
Zusammen mit einem ''Shared Pointer'' Mechanismus\footnote{Shared Pointer sind Mechanismen die dafür sorgen dass allozierte Objekte automatisch freigegeben werden, sobald sie nicht mehr verwendet werden (vgl. \cite{boostSmart}). } und dem Singleton Entwurfsmuster (siehe \cite{gof04}) kann man dafür sorgen, dass ein Janitor-Objekt, von mehreren Stellen aus, gleichzeitig benutzt werden kann.\\
Da nach jeder Graphränderung eine Prozess-Liste (siehe \ref{process}) erstellt werden muss, existiert mit dieser Lösung ein weiterer Vorteil:
Die Prozesslisten Erstellung könnte ebenfalls mit dem Destruktor des Janitors abgearbeitet werden. Somit würde Automatisch die Prozessliste nach jeder Änderung angepasst werden.
\\\\
\begin{lstlisting}[label=janitor, caption=Lösung des Nebenläufigkeitsproblemes durch den Janitor]


// Datei Janitor.h

class Janitor {
private:
	Graph *graph;
public:
	Janitor( Graph *graph ) : graph(graph) {
		// Graph-Prozess sperren
		graph->mutex.lock();
	}
	
	virtual ~Janitior() {
		// Prozessliste erstellen
		// ...
		// Graph-Prozess entsperren
		graph->mutex.unlock();
	}
	
	void veraenderGraph() {
		graph->veraenderGraph();
	}
};

// Datei Graph.h

class Graph {
friend class Janitor;
public:
private:
	Mutex mutex;
	void veraenderGraph() {
		// ...
	}
public:
	void prozess() {
		// bearbeite Graph
	} 
};	

// Datei GUIController.cpp

void GUIController::veraenderGraph() {

	Janitor janitor ( getGraph() ); // konstruktor sperrt Graph-Prozess
	janitor->veraenderGraph();
	// ...
	// ...

} // janitor verlaesst Gueltigkeitsbereich 
  //  und entsperrt Graph-Prozess
\end{lstlisting}
